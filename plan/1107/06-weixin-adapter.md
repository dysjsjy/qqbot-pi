# 06 微信群接入 MVP

## 1. 主线修订

新增需求以群聊和全天分析为主，因此移除原“服务号作为微信主线”的安排。微信目标是一个真实微信群：采集未 @ 文本、响应群命令、基于本群记忆回答，并主动发送定时报告。

服务号/微信客服的一对一回调不能证明微信群能力；企业微信若采用另一产品体系，也必须验证是否能采集非 @ 群消息，不能仅凭有群推送 webhook 就判定满足要求。

## 2. M0 必须解决的外部依赖

选择一个现成、可访问且具有所需权限的微信群网关，只支持一个固定版本。具体供应方尚未确定，这是当前计划的关键前置项，不能在文档中假定已经可用。

| 能力探针 | 最小证据 |
| --- | --- |
| 登录与状态 | 已登录账号、失效事件、恢复方式；明确是否需要人工重新登录 |
| 全群文本接收 | 两名成员发送 20 条文本，含至少 15 条未 @，均可读取原文和来源 |
| 稳定身份 | 群 ID、发言者 ID、消息去重字段；昵称变化不影响身份 |
| @ 与命令 | 区分 @ 本机器人、@ 他人、普通正文；斜杠命令可识别 |
| 主动发送 | 没有新用户消息时可向指定测试群发送文本 |
| 连通性与历史 | 断线通知、重投/重放规则、能否补历史；不支持也必须明确记录 |
| 使用条件 | 协议版本、凭据、额度/费用、运行环境及维护责任有记录 |

建议 M0 限时 3 个工作日与其他探针一起完成。若没有可用网关，继续 QQ/RAG/网页开发，并将微信里程碑记为 BLOCKED；不把自研微信登录/客户端协议加入 MVP，也不宣称已完成双平台目标。

## 3. Java 适配器契约

由选定网关的 HTTP callback、WebSocket 或长轮询方式实现适配，内部统一使用：

```text
receive -> InboundGroupMessage
sendGroupText(groupId, text, clientRequestId) -> accepted / rejected / unknown
connectionState -> online / offline / auth_expired
capabilities -> 普通群文本、主动发送、历史补齐、发送幂等能力
```

以上是本项目接口，不是假定网关具有这些同名 API。M0 产出实际字段映射和脱敏请求样本；若网关不支持 clientRequestId 幂等，记录为不支持并使用 UNKNOWN 语义。

- 入口验证网关凭据和实际账号，禁止只信任回调 body 中的 groupId/账号声明。
- 只采集启用群，保存未 @ 文本；自己的发送回声不进入 RAG 和日报。
- 所有命令复用 Java 公共模块，群管理员使用稳定 userId 白名单。
- 登录失效后停止派发该账号的群发送，网页显示失败原因；恢复连接不自动消除数据缺口。
- 不自行重放无法确定是否已送达的群消息；日报记录保留供管理员核对。
- 若接入只能获取 @ 消息，判定此路线不满足 M0，不悄悄降级成“全天分析”。

## 4. 实施与验收

- [ ] WX-01：真实网关探针、版本固定、字段与认证映射。
- [ ] WX-02：事件接收、普通文本采集、去重及群白名单。
- [ ] WX-03：命令、@ 问答和主动文本发送。
- [ ] WX-04：登录失效、断线缺口、重连重复投递和未知发送状态。

AC-WX-01 与 QQ 使用相同的真实群闭环：20 条文本（至少 15 条未 @）、5 次 @ 问答、全部常用命令、一次不依赖新用户消息的主动日报；验证登录失效可见、重连不重复入库。真实截图/回执必须来自所选微信群，而非服务号或模拟器。

## 5. MVP 不做

历史消息爬取、客户端协议逆向、多个网关热切换、附件解析、朋友圈、私聊机器人、企业微信与个人微信双重兼容。本方案只要求接入启用之后的可接收文本，已知缺口在日报中说明。
