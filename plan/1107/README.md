# QQ / 微信群聊 Bot MVP 计划

更新日期：2026-11-07。状态：实施中，已有代码与本地验证，真实双平台验收待完成。需求依据：[新增需求原文](tmp.md)。本轮将群聊、RAG 持久记忆、定时分析和 React 管理端纳入首版，并收敛原方案的工程与运维范围。当前进展见 [实施与验收证据](evidence/implementation.md)，启动方法见 [项目说明](../../README.md)。

## MVP 要验证的闭环

**授权群文本采集 → 群内命令 / pi 问答 → 群级 RAG 记忆 → 每天 09:00 分析昨日完整采集记录 → 发回原群 → 管理员网页查看与配置。**

- 后端以 Java 为主，Spring Boot 单体；通过官方 JSONL RPC 运行 pi，Node.js 只承载 pi。
- 管理端使用 React + TypeScript，提供登录、群配置、记忆查询、定时任务与执行结果；静态资源随 Java 服务发布。
- PostgreSQL + pgvector 同时保存消息、向量、任务和发送状态；单实例、单管理员、最多 5 个授权群。
- QQ 和微信各选择一种能获取未 @ 群消息、识别发言者并主动发群消息的接入方式。微信主线改为群聊接入，服务号不再充当微信群方案。

## 本次范围调整

| 原计划 | MVP 修订 |
| --- | --- |
| 群内只处理 @；未 @ 消息忽略 | 授权群全部可接收文本落库，只有命令 / @ 问答 / 定时分析触发生成 |
| 微信服务号主线 | 微信群接入主线；具体网关在 M0 实测选定，不自行研发登录协议 |
| 记忆、定时任务、网页后台延后 | 三项均为本次 MVP 必须交付能力 |
| 多 Maven 模块、8 个 pi 进程、24 小时压测及完整运维门槛 | 单 Maven 应用按包分层、最多 2 个 pi 进程、2 小时冒烟和一次备份恢复 |
| 双平台私聊是必验场景 | 双平台群聊是必验场景，私聊与频道后续再做 |

## 完成标准

1. QQ、微信各至少一个真实群，普通文本能采集，命令能响应，非 @ 发言不自动产生聊天回复。
2. `/help`、`/new`、`/cancel`、`/memory <问题>`、`/summary yesterday` 行为符合权限及作用域。
3. 群消息持久化并可语义检索；重启后仍可用，答案带来源，不串群。
4. 每日 09:00（Asia/Shanghai）按昨日 `[00:00, 次日00:00)` 的已采集全文生成摘要并发回原群；缺口与非文本排除情况明确标注。
5. React 页面可完成配置、检索与运行记录查看，任务修改在重启后保持。
6. [08](08-acceptance.md)的 24 项 MVP 必验项全部通过；未执行项不标为完成。

## 推进与估算

M0 能力探针 → M1 Java/pi 与采集底座 → M2 双平台群聊与命令 → M3 RAG → M4 定时分析 → M5 React → M6 联合验收。以一名熟悉 Java、能开发 React 的开发者估算 **26 个开发工作日 + 5 天缓冲**；账号、网关和平台权限等待另计。
